# wgpu #8518：真实 render 流程与局部 folding 成本复核

日期：2026-09-19。延续[局部 folding 实验](issue_8518_texture_folding_result.md)，本轮补足真实附件写入与后续采样流程，先控制测量波动，再定位并修正一个具体的分配问题。

**当前结论：本机代表性 render 场景已验证局部收益，保留局部 folding 与矩形合并修正；暂不扩大完整 tracker folding，整体合入验收仍未完成。**

## 范围与场景

代码工作区为 `/Users/lijinlei/Rust/forks/wgpu-issue-8518-folding`，分支 `codex/issue-8518-texture-folding`。基线仍为 `f12c3e4508cb706c1e1faeb973bdb9c6970f5e15`。原永久缓存分支保持不动。代码已提交并推送为 [`f47afd2b6`](https://github.com/jinleili/wgpu/commit/f47afd2b6aa8872eb283e808363e180f3930e9e3)，未创建 PR。

旧 `Texture Initialization` 基准中的附件场景只带 `RENDER_ATTACHMENT` usage，执行的是 compute dispatch。本轮新增 `Texture Init Render`，真正执行 render attachment 写入和后续 fragment shader 读取。它是合成的代表性流程，不是正式应用的帧率验收。

四个独立 benchmark：

- **共享附件**：16 对纹理，每个纹理 3 mip；先逐 mip 渲染写入，再由 1,000 个不同 bind group 在 10 个 render pass 中读取，共 10,000 次消费 draw。
- **重叠混合 view**：每对纹理包含一个渲染附件和一个提前上传的普通纹理；两种 view 覆盖 mip 0–1、1–2，跨组共享并重叠。
- **discard 后采样**：与混合场景相同，但在第 5 个消费 pass 后重新渲染附件并使用 `StoreOp::Discard`，随后继续读取同一批组。此时附件必须清零，普通纹理仍保留上传内容。
- **无采样纹理对照**：相同的消费 pass、绑定和 draw 数，使用空 bind group 与常量颜色 shader；仍然有输出附件，不能称为完全没有纹理的流程。

纹理为 4×4、`Rgba8Unorm`。shader 使用 `textureLoad` 读取两个 mip，排除 sampler 过滤成本。每个场景计时前运行 8 次预热并读回输出像素；discard 场景检查附件为零与普通纹理非零的混合结果。测试模式缩为 8 个组、2 个消费 pass。

## 测量与噪声

硬件为 Apple M1 Max，Metal 后端。与上一轮相同 bench profile、默认 benchmark features，额外 backend/Metal 调试验证关闭，core API 验证保留，`RAYON_NUM_THREADS=8`。每个场景、每个版本独立启动进程，避免前序场景留下不同资源和分配历史。正式测量期间没有运行本任务的构建、测试或 profiler；没有关闭用户应用或修改系统调度策略。

每个进程执行 128 次编码和提交，另外执行 128 次创建 1,000 个 bind group。descriptors、entries 与创建结果容器容量在计时外准备，销毁和 GPU 等待排除。编码与提交分别计时。这里的 CPU 侧耗时是 API 调用的墙钟时间，包含可能的调度等待，不是硬件 CPU cycle 数；不代表 GPU 时间或帧率。

先用同一 trunk 二进制做两组 A/A：每组四次运行，比较中间两次与前后两次的均值。四场景共 32 个进程。编码＋提交的八组差异落在 **−0.93%～+1.58%**。这是本轮观测到的噪声范围，不是未来测量的误差保证。

随后做四组 ABBA/BAAB，每组分别对两个 A 与两个 B 取均值，再计算 B/A 的百分比；汇总取四组百分比中位数。四场景共 64 个进程。场景顺序按固定种子改变，组内顺序交替。表格的绝对耗时是四组均值的中位数，因此其比值与“配对百分比中位数”可能略有不同。

独立进程、增加预热和分组配对同时改变，未做逐因素实验。因此本轮证明测量波动有所收敛，没有证明旧波动仅由某一个因素造成。

## 分配与采样诊断

诊断使用独立构建的二进制，临时全局 allocator 包装器只在调用线程的编码＋提交和创建区间计数。统计 Rust 的分配/重分配次数、申请字节与净存活增量；不包含 Metal/Objective-C 原生分配，也不覆盖异步线程。重新分配计为一次申请和一次释放。诊断时间不计入正式性能结果，所有探针在构建后从待交付源码移除，保留在忽略的诊断产物目录。

初版在共享附件与重叠混合场景均比 trunk 每轮多 **46 次**分配/重分配、**23,976 字节**累计申请量。源码表明：连续登记单 mip，以及相同 layer 范围的重叠 mip view，都会让原先内联的矩形提前升级成 `Box<TextureInitTracker>`。

本轮只改进这一规则：当两个范围在一个维度相同，另一个维度相邻或重叠时，矩形并集继续内联保存。具有缺口、不能精确表示成一个矩形的范围仍使用复杂 tracker。返回 action 仍保留原始顺序和 kind；没有把包围盒中的缺口误认为已登记。原有 discard 就地清零和提交顺序语义不变。

另对共享附件、重叠混合场景的两种初版二进制各采样 3 秒，四次均确认未跨出编码测量阶段。可见初始化登记栈在初版 folding 中分别为 12、16 个样本，对应 `CommandEncoder::finish` 的 709、856 个样本。采样包含 allocator 探针、函数内联及调度影响，不能据此得出精确 CPU 占比或优化上限；它没有显示剩余初始化登记仍为主要热点。

当前不扩大 scope → command buffer → device 的重构范围。已有证据支持先修正可复核的分配成本，不能支持“完整 folding 一定有更大收益”。

源码还显示两条路径的触发时机不同：render pass 的 usage scope 在 `set_bind_group` 时合并设置过的组，初始化需求则在实际刷新有效绑定时登记；compute 的 usage scope 又按 dispatch 合并。直接把初始化放进所有 usage 合并调用，可能增加未实际使用资源的初始化需求。进一步整合需要证明语义与工作量，而不只是减少一段循环。

### 矩形合并后的分配结果

相同诊断方法下，最终版本在三个纹理场景均比初版少 32 次分配/重分配、12,544 字节累计申请量。各版本每轮编码＋提交的中位数如下：

| 场景 | trunk 分配次数 | 初版 folding | 矩形合并后 | 最终比 trunk 多申请字节 | 最终比 trunk 多的峰值净存活字节 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 共享附件 | 811 | 857 | 825 | 11,432 | 5,816 |
| 重叠混合 view | 517 | 563 | 531 | 11,432 | 5,816 |
| discard 后采样 | 1,055 | 1,097 | 1,065 | 15,656 | 5,816 |
| 无采样纹理对照 | 198 | 200 | 200 | 392 | 280 |

最终版本的局部状态仍有成本，没有变成零分配。计数区间结束时，四个场景的净存活增量均与 trunk 相同；这只说明当前线程、当前区间的额外申请已经抵消，不能推导为整个进程没有内存增长。新建 1,000 个组的分配计数和字节数在三个版本完全一致：纹理组 9,000 次、984,000 字节，空组 2,000 次、512,000 字节。

正式初版测量的进程最大 RSS 中位数，trunk/folding 分别为：共享附件 94.0/95.5 MiB、重叠混合 64.1/64.4 MiB、discard 95.3/97.7 MiB、对照 31.7/31.7 MiB。RSS 包含驱动、资源创建与整个进程生命周期，不能把这些差值直接归因于局部 tracker；它不替代上面的区间分配统计，也不能证明高 texture index 场景的内存上界。

三个纹理场景的四组配对均改善，最终版本各组差异均大于本轮 A/A 观测到的最大偏移；无采样纹理对照接近零。结合固定工作量、像素检查和独立分配计数，本机证据已经支持这些 render 场景中的局部收益。四组数据仍不足以承诺跨机器或真实应用的收益幅度。

两批都与 trunk 配对，初版与矩形合并版本没有直接交错比较。因此可以确认矩形合并减少了分配，并确认最终版本相对 trunk 的收益；不能把前后两批百分比之差精确归因于这段修改。

创建成本已按明确频率合并计算，没有把“创建增加百分比”与“编码下降百分比”直接相减。正式应用若长期复用组，应按自身每帧创建次数计算，不能直接套用全部重建的列。创建和编码分阶段测量，这一列是按频率相加的成本估算，不是实际每帧创建后立即绑定新组的流程实测。

## 判定与限制

本轮已经达到“真实附件流程＋可靠对照＋可解释的局部成本修正”的完成标准。局部 folding 值得保留，不能再仅依据旧 compute 数据将它判为整体无收益；也不能据此认为完整 scope → command buffer → device folding 必然值得继续扩大。

这里的收益只适用于本机、所列资源规模和合成 render 流程。本轮没有重新测量完整 compute/render benchmark 矩阵，没有正式应用帧率验收、Linux Vulkan/Lavapipe poison-memory 或 CTS。高 tracker index 下稠密数组的内存成本仍是边界。新像素读回和已有 CPU 枚举都不能替代 poison-memory 验证。因此，当前仍不把候选标为整体可合入，也不据此关闭 #8518。

下一项合入前证据应来自 Lavapipe poison-memory（Windows 原生也可运行）与目标应用 CPU 路径；在现有本机采样未发现足够大的剩余初始化热点时，停止扩大架构改动。
